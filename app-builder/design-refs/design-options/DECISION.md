# Examples page options -- structural differences

**Option 1 -- Story stack:** Multi-section long-form story per app. Features list leads, then a horizontal (or desktop grid) screenshot strip, then prompt / brand / provenance panels at the bottom.

**Option 2 -- Hero shot:** Full-bleed production screenshot owns the first viewport. A three-metric strip (crops / windows / zones) sits under the hero. Compact catalogue rows list each shipped app -- no multi-panel story body.

**Option 3 -- Card catalog:** Filter-chip chrome plus equal magazine cards. Overlapping stacked device frames are the card face; title, stat chips, and actions sit under the stack. Screenshots are not a strip and not a full-bleed hero.

Separable pieces for a mix: what leads (features / hero media / card face), screenshot presentation (strip / full-bleed / stacked devices), chrome (story sections / metrics rail / filter catalog).

## How the three differ structurally

These are three different layout architectures, not one skeleton recoloured:
option 1 is a stacked long-form story (sections down the page, screenshots as a
horizontal strip), option 2 is a full-bleed hero card above compact catalogue
rows, and option 3 is an equal-weight card grid with filter chrome and stacked
device frames as the card face. Swapping palettes on any one of them does not
produce either of the others.

## Chosen

**Option 3 -- Card catalog.** Chosen by the user on 2026-08-02.

Why: the examples page has to hold a growing set of shipped apps and let a
reader compare them, which is a catalogue problem rather than a story problem.
Equal magazine cards keep every app legible at the same weight, the stacked
device frames show desktop and mobile in one card face without a strip that
scrolls off, and the filter chips scale as the set grows. Option 1 buries the
second app below a long story; option 2 gives the first app a full-bleed hero
and demotes the rest to rows.

Required addition beyond the mockup, per the user: each card expands into a
detailed "What it does" breakdown under the images -- grouped capability
sections in plain prose, closing with a "The app it shipped" paragraph citing
real gate numbers from a dated run. Every figure must come from a real
measurement, never an estimate; the QuickFlight entry is the reference for tone
and depth.
