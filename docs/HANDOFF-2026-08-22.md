## The honest verdict first

**The night's stated deliverable was not delivered.** The concept was a job
application site, built end to end through the 24-step n8n pipeline, prd through
ship. It reached step 3 of 24 and was stopped. As of this writing a second run
is in flight, started 15:59 UTC on 2026-08-22, past `prd` and `product`.

There is no app. `job-application-site/` contains `docs/`, `design-refs/` and
`public/` -- no `src/`, no `package.json`, no repo, no deploy, no URL. By the
standing rule that an app is not done until it is shipped, nothing shipped.

A lot of real work landed, and it is worth separating from the miss below rather
than letting either hide the other.

## Why it did not finish

Three reasons. One is a genuine constraint, one is a genuine mistake, and the
third is a consequence of the first two.

**1. Constraint: the session cannot relaunch itself.** The plan depended on
auto-resume across token and session limits. `scripts/overnight/resume.ps1` was
written and both of its refusal guards were executed and observed refusing -- a
night-complete marker and a live lock each returned in 0s having launched
nothing. Its LAUNCH path was never exercised, because the harness classifier
refuses to let this agent spawn a nested
`claude -p --dangerously-skip-permissions` session. Registering a scheduled task
to do the same thing is the same act with extra steps, so it was not done. The
script sits on disk unarmed. The owner can arm it with:

```powershell
schtasks /create /tn "RedAnvil Night Resume" /tr "powershell -NoProfile -ExecutionPolicy Bypass -File C:\Users\brian\RedAnvil\scripts\overnight\resume.ps1" /sc minute /mo 20 /f
```

**2. Mistake: the build was stopped and never restarted.** At step 3 the PRD was
found to describe a marketplace for a prompt that says "it is not a
marketplace", and stopping was correct -- 21 later roles would have built it
faithfully. Hours then went into fixing the PRD typing, the auth identity and
the entities field. All three were prerequisites for restarting. All three were
finished around 01:00. The build was not restarted. A design request arrived and
was followed instead. The prerequisites were completed and the thing they were
prerequisites FOR was not, which is the single largest failure of the night and
is not attributable to any tool.

**3. Consequence: every continuation came from the owner.** With no self-resume
and no restarted build, the session advanced only when prompted. "Fully
autonomous" was never actually running.

### The PRD described the wrong product, four times over

This is the substance of the night. A build produced an 80KB internally
consistent PRD for the wrong product, which is the documented failure mode where
a wrong spec is worse than a crash.

| field | first run | after fixes |
|---|---|---|
| appType | `"Marketplace"` | `"SaaS"` |
| hasAuth | `false` | `true` |
| entities | `["Spreadsheet"]` | `["Application"]` |
| title | `"Real"` | `"Job application Site"` |
| "fully public -- no register/login" | present | gone |
| pronoun feature names | 3 | 0 |

**Negation blindness -- `8f35e16`.** `ANSWER_RULES` matched `marketplace` inside
"it is not a marketplace". The sentence whose entire job is to rule the category
out is what selected it. Matching is now clause-scoped, so
"it is not a marketplace, it is a job board" still answers job board rather than
vetoing the group. Proven by disabling `clauseIsNegated`, which fails exactly the
two negation tests with the original symptom.

**Provenance recorded intent, not outcome.** A run could record
"sign-in: Yes" while the PRD said `hasAuth: false`, with nothing able to say
which was real. The role now reads the control's value back off the DOM and
refuses to write a PRD when they differ.

**Positional identity -- `e3e4fde`.** `authRequiredByFeatures` matched
`f.id === 'F3' && f.name === 'Accounts'`. In that document the accounts feature
is **F8**, because eleven capability-derived features are numbered ahead of it,
and F3 is "Ones They Sent grid". So an explicit sign-in answer was discarded in
silence. Every FeatureSpec now carries a `role` discriminant. Reverting
`isAccountsFeature` to the positional form fails a dedicated test.

A wart in the delegated version was caught and removed: both branches of
`authRequiredByFeatures` returned `true`, so `some(isAccountsFeature) ? true :
true` read as a decision while making none.

**The entities field was never filled -- `2f59e51`.** `generate.ts` reads
`listed.length > 0 ? listed : deriveEntities(prompt)`, where `listed` is the
wizard's own entities control. The wizard has always had that input
(`ScopeStep.tsx`, `id="wizard-entities"`) and `prd.mjs` never touched it, so the
builder fell back to guessing domain nouns from prose. Stating the entities beats
improving the guess. `sanitiseEntities` rejects rather than repairs -- pronoun
heads, case-insensitive duplicates, anything outside a conservative character
class, capped at five. `Job; rm -rf /, Application` is rejected.

### The 22-rule CI mystery, diagnosed -- `054e4ca`

`results-provenance` had failed for days with only
"committed 83/83, reproduced 61/83" -- unactionable, because it never said WHICH
22. Four lines were added to print the two rule-id sets, which the script
already held in memory. On its first real CI run it named them.

**Every one of the 22 is a recorded-verdict rule. Not one is a deterministic
measurement.** That kills the standing assumption that CI lacked a browser or a
tool; `verdictsHash` matches, so the file is byte-identical in both places. The
same job's log carries the mechanism:

```
fe-fail-closed-states: 3 file(s) under review changed since 466b15be5a28
```

It is the verdict-staleness treadmill. A verdict is pinned to the commit it was
recorded at, every later commit changes files under review, and the verdict
silently stops counting. The committed result claims 83/83 because all 83 were
fresh when it was written, and it can never reproduce again after any commit
touches a reviewed file -- which every commit does, including the gate's own.

`results-provenance` is therefore STRUCTURALLY red. Re-gating cannot converge it.
The real fix is pinning each verdict to the source commit of the files it
reviews rather than to repo HEAD. Not attempted.

## Things worth not relearning

**Waiters must poll the right process name.** Three hung Grok runs were read as
"died" because the loop polled `node.exe` while Grok runs as `grok.exe`.

**A content fingerprint is not a timestamp.** The first restart attempt today
refused with "no artifact under docs/PRD.md changed" even though the file was
rewritten seconds earlier. It was byte-identical to the manual run from 01:00.
The check was right; the initial condition was dirty. A fresh build needs no
prior artifacts.

**`git show <rev>:<path>` breaks under Git Bash.** MSYS rewrites the colon into
a path and the command fails. Prefix `MSYS_NO_PATHCONV=1`.

**Grok wrote scratch into the app root** -- `index.html`, `mark-01.png` and two
32px PNGs landed beside `docs/`. Removed. The `--cwd` scope is the app
directory, so nothing stopped it.
